## はじめに

**本記事は、さくらのクラウド検定 学生アンバサダーとして執筆しています。**

こんにちは。学生エンジニアです。

私はさくらのクラウドで、性格の違う2つのものを動かしています。

1. **Webサーバー**：水田の水管理支援Webアプリ「スイスイナビ」のPython API。24時間ずっと動かしておくもの。
2. **GPU**：AIのコーディング支援に使う大きな言語モデル。必要なときだけH100を借りて動かすもの。

使い方はまったく違うのに、どちらも**Docker**で動かしています。この記事では、それぞれの場面でDockerが何を楽にしてくれたのかを、実際の設定ファイルと一緒に紹介します。

## 先に、Dockerとは

Dockerは、アプリと、その動作に必要なもの（Pythonのバージョンやライブラリなど）を、まとめて1つの「箱（コンテナ）」に入れて動かす仕組みです。箱の作り方は `Dockerfile` に、複数の箱の起動のしかたは `docker-compose.yml` に書きます。

一度箱の作り方を書いておけば、Macでも、さくらのクラウドのサーバーでも、同じ箱が同じように動きます。これが、以下の話すべての土台です。

## 第1部：Webサーバー編（さくらのクラウドのサーバー）

### 何を動かしているか

スイスイナビのAPIは、さくらのクラウド（東京第2ゾーン）のUbuntuサーバーで、3つの部品として動いています。

```
 ブラウザ ──(HTTP: 80番)─▶ [パケットフィルタ]
                              ▼
                 さくらのクラウド上のUbuntuサーバー
                 ┌──────────────────────────────┐
                 │ Caddy ──▶ API(FastAPI)        │
                 │  :80        │                 │
                 │             ▼                 │
                 │       PostgreSQL               │
                 └──────────────────────────────┘
```

Caddy（入口）、API（FastAPI）、PostgreSQL（データベース）が、それぞれ1つのコンテナです。

### 良い点1：3つの部品を、1つのコマンドで起動できる

```bash
sudo docker compose -f docker-compose.yml -f docker-compose.vps.yml up -d --build
```

これだけで3つのコンテナが立ち上がります。しかも、**データベースが正常になってからAPI、そのあとにCaddy**という順番も守ってくれます。手でサービスを1つずつ起動する必要はありません。

`-f` を2つ並べているのは、基本の設定にサーバー用の設定（Caddyの追加）を重ねるためです。Macでは基本の設定だけ、サーバーでは2つを重ねる、という使い分けができます。

### 良い点2：Macで試したものを、そのままサーバーに持っていける

私のMacのシステムのPythonは3.9.6ですが、このAPIが想定しているのは3.12です。直接サーバーに入れるなら、バージョンの違いに毎回気をつける必要があります。

Dockerなら、箱の中に必要なPythonが入っているので、自分の機械の都合に左右されません。実際、サーバーに載せる前に**同じ構成をMacのDockerで動かして**、テスト（本物のPostgreSQL相手で110件）を通しました。おかげで、サーバーで何か起きたとき、「原因はコードではなくサーバー側」と切り分けられました。

### 良い点3：サーバーのOSを汚さない

PostgreSQLやPythonのライブラリを、OSに直接インストールしなくて済みます。やり直したくなったら、箱を消して作り直すだけです。サーバーにはDockerだけを入れました。

### 良い点4：再起動しても、勝手に戻る

3つのコンテナには `restart: unless-stopped`（止められていない限り再起動する）を付けています。Docker自体もサーバーの起動時に自動で立ち上がります。

実際にサーバーを再起動して、Macから3秒ごとに `/api/health` を呼び続けてみました。**再起動の指示から27秒後に**、誰もログインしないまま、APIが元どおりに答えました。データベースの中身も残っていました。

### 良い点5：小さなサーバーで足りる

動かしてみると、3つのコンテナの合計メモリは約150MiB（Caddy 53・API 64・PostgreSQL 34）、システム全体でも2GB中592MiBでした。Docker自体が重くて困る、ということはありませんでした。

### 気をつけたこと

Dockerは便利ですが、層が1枚増えるぶん、知らないと危ないこともあります。

- **Dockerが公開したポートは、サーバー内のファイアウォール（ufw）をすり抜けることがあります**（Docker公式の説明より）。そこで、サーバーの外側にある**さくらのクラウドのパケットフィルタ**で、22番（SSH）と80番（HTTP）以外を止めました。外から8000番と5432番に接続すると、タイムアウトになることを確かめています。
- **`docker` グループには入りませんでした。**このグループに入ると、実質的にroot（管理者）と同じ権限になるからです。`sudo docker ...` で使っています。
- **Dockerは公式リポジトリから入れ、署名用の鍵の指紋を確かめました。**ダウンロードした鍵が本物かを、Dockerが公開している指紋と見比べてから登録します。
- **秘密情報は箱に入れません。**データベースのパスワードなどは、サーバーの上で乱数から作った `.env` ファイル（権限 `600`）に置き、コードと一緒には送りません。

### ところで、レンタルサーバでは？

スイスイナビの画面（HTMLやJavaScript）は、さくらのレンタルサーバで公開しています。レンタルサーバは静的なファイルの公開には向いていますが、共有環境なので、Dockerや常に動き続けるPythonを自由に動かすことはできません。そこで、**画面はレンタルサーバ、APIはDockerでさくらのクラウド**、と役割を分けています。

## 第2部：GPU編（高火力 DOK）

### 何を動かしているか

もう1つは、AIのコーディング支援に使う大きな言語モデルです。私のMacはM1 Max（メモリ64GB）ですが、使いたいモデルにはメモリが足りません。そこで、さくらの**高火力 DOK**でNVIDIA H100を借りて動かしています。

DOKは、サーバーを借りるのではなく、**コンテナを渡して、タスクとして実行してもらう**サービスです。

### 良い点1：DOKでは「イメージ＝デプロイ」

DOKにはSSHで入るサーバーがありません。コンテナイメージとプランと環境変数を渡すと、DOKがタスクとして実行します。つまり、ここではDockerは選択肢の一つではなく、**唯一の使い方**です。

逆に言えば、タスクに必要なものはすべて `Dockerfile` に書かれています。手で設定したサーバーの中身を、あとで思い出す必要がありません。

### 良い点2：CUDAを自分で入れなくていい

GPUを使うときに一番大変なのは、たいていドライバーとCUDAの準備です。Dockerなら、GPU用のライブラリが入ったイメージから始められます。

- Ollama版は `ollama/ollama`
- DeepSeek版は `ghcr.io/ggml-org/llama.cpp:server-cuda-v0.5.0`

ドライバーはDOKのホスト側、ライブラリはベースイメージの中にあります。私の `Dockerfile` では、その上に小さなPythonのゲートウェイ（認証付きの入口）を足しているだけです。

```dockerfile
FROM ollama/ollama:${OLLAMA_VERSION}
RUN apt-get update && apt-get install -y --no-install-recommends python3 python3-venv ...
COPY backend/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY backend/ .
CMD ["./start.sh"]
```

推論エンジンを替えたいときも、ベースイメージを差し替えた `Dockerfile` をもう1つ書くだけでした。Mac側のクライアントから見ると、どちらも同じ8080番のゲートウェイです。

### 良い点3：料金の仕組みと相性がいい

ここがGPUならではの話です。DOKのH100プランでは：

- 実行時間は秒単位で課金（¥0.28/秒、税込で約¥1,008/時間）
- **イメージのpull（取得）時間と、待ち時間は課金されない**
- イメージは最大30GB

つまり、モデルを**イメージの中に入れておけば、取得は無料**です。起動してからモデルをダウンロードすると、その時間はH100の料金がかかります。そこで、ビルド時にモデルを入れられるようにしました。

```bash
docker build --build-arg BAKE_MODEL=gpt-oss:20b .
```

`gpt-oss:20b`（約14GB）は30GBに収まります。`gpt-oss:120b`（約65GB）は収まらないので、起動時にダウンロードするしかありません。DOKの回線（250Mbps）だと計算上は35分以上、約¥600かかります。

【要計測：モデル入りイメージと、起動時ダウンロードの、実際の起動時間】

### 良い点4：GitHubでビルドして、さくらのレジストリに送る

大きなイメージを自宅の回線でアップロードするのは大変です。そこで、GitHub Actionsでイメージを作り、**さくらのコンテナレジストリ**に直接送っています。

```yaml
- uses: docker/build-push-action@v6
  with:
    file: ${{ inputs.dockerfile }}
    platforms: linux/amd64
    push: true
    tags: |
      ${{ inputs.registry }}/${{ inputs.image }}:latest
      ${{ inputs.registry }}/${{ inputs.image }}:${{ github.sha }}
```

- **`linux/amd64`**：DOKのホストはamd64、MacはARMです。GitHub側で作れば、Macで別のCPU向けにビルドしなくて済みます。
- **コミットごとのタグ**：どのタスクも、特定のバージョンのイメージを指定できます。元に戻すときはタグを1つ変えるだけです。

### 気をつけたこと

- **何も残らない。**タスクが終わると、アーティファクト用の場所以外はすべて消えます。だからこそ、モデルをイメージに入れておく意味があります。
- **`SAKURA_` で始まる環境変数は、DOKが予約しています。**そのため、ゲートウェイは `GATEWAY_API_KEY` という名前でもAPIキーを受け取れるようにしました。キーがなければ、認証なしで動くのではなく、エラーを出してすぐに止まります。
- **起動には時間がかかる。**Macならすぐ使えますが、DOKはタスクの起動を待つ必要があります。【要計測：タスクを投入してから、最初の返事が来るまでの時間】
- **実行時間の上限を必ず設定する。**初期値は20日です。止め忘れると、H100の料金がそのまま積み上がります。

## 2つを比べると

| | Webサーバー編 | GPU編 |
|---|---|---|
| さくらのサービス | さくらのクラウド（サーバー） | 高火力 DOK |
| 動かし方 | 24時間ずっと | 必要なときだけ |
| Dockerの役割 | 3つの部品をまとめて起動・自動復帰 | イメージそのものがデプロイの単位 |
| いちばん助かった点 | Macで試した構成がそのまま動く | CUDAの準備が不要、モデル入りで取得が無料 |
| 注意点 | ufwをすり抜けるポート | 何も残らない、起動待ち、止め忘れ |

使い方が正反対でも、「**箱の作り方をファイルに書いておけば、どこでも同じように動く**」というDockerの良さは共通でした。

## まとめ

さくらのクラウドでDockerを使うと：

1. 複数の部品を1つのコマンドで、正しい順番で起動できる
2. Macで試した構成を、そのままサーバーやGPUに持っていける
3. サーバーのOSを汚さず、やり直しが簡単
4. 再起動しても自動で戻る（実測27秒）
5. GPUでは、CUDAの準備が要らず、モデルをイメージに入れて取得料金を節約できる
6. GitHubでビルドして、さくらのコンテナレジストリに直接送れる

一方で、層が1枚増えるぶん、ポートの公開や権限には注意が必要です。私は、さくらのクラウドのパケットフィルタを外側の守りにすることで、それを補っています。
